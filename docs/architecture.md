# Family Law Wise 架构

页面用 Next.js，数据库用 Supabase 的 Postgres，文件用 AWS S3。后段的抽数和 CIS PDF 仍写在这个系统里，不另起 Spring Boot，也不把数据库迁到 RDS。

配套计划见 `docs/nj-cis-plan.md`。

## 为什么是这三样

清单、问卷、已确认金额和 CIS 格子都是关系数据，Postgres 够用。Supabase 提供这份 Postgres，以及律师登录和客户一次性验证码。

税表、工资单和对账单放在 S3 私有桶。打开文件时由 Next.js 服务端检查权限，再签发短时链接。桶不公开。

CIS 难在财务事实和表格格子的对应，不在换一套 Java 服务。Spring Boot 和 RDS 不作为本产品的运行架构。

## 运行时

```
浏览器
  律师端 / 客户端（Next.js）
        │
        ▼
Next.js 服务端（Vercel）
  登录会话、权限、清单规则、CIS 映射
        │
        ├── Supabase Postgres    事项、问卷、清单、财务事实、CIS 草稿
        ├── Supabase Auth        律师登录、客户验证码
        └── AWS S3               原始文件
```

邮件用 Resend，从 Next.js 服务端发出。邀请和缺件各走一封邮件。

本地开发连 dev 项目和 dev 桶。生产用另一套 Supabase 项目和另一个 S3 桶。预览部署不连生产库，也不连生产桶。

## 文件怎么走

1. 浏览器向 Next.js 要一个上传地址。
2. 服务端确认这个人属于该律所、该事项，然后给 S3 一个短时上传许可。
3. 浏览器把文件直接传到 S3。
4. 服务端写入文件记录：事项、上传人、原始文件名、S3 对象键。数据库里不存文件正文。
5. 律师或客户再次打开时，服务端重新检查权限，签发短时下载链接。链接过期后不能继续用。

对象键按律所和事项分开，例如 `firms/{firmId}/matters/{matterId}/{documentId}`。知道链接规律也不能读到文件，因为桶策略拒绝公开读取。

## 数据放哪里

| 数据 | 位置 |
| --- | --- |
| 律所、用户、事项、当事人 | Postgres |
| 问卷答案、清单项、活动 | Postgres |
| 已确认金额及其来源 | Postgres |
| CIS 草稿和导出版本 | Postgres |
| PDF、图片原件 | S3 |
| 登录会话 | Supabase Auth |

每一行业务数据带 `firm_id`。查询在服务端按律所过滤。客户只能碰到自己被邀请的事项。

问卷答案、清单项、文件、抽取结果、已确认财务事实分开存。一份文件可以对应多项清单。一项清单可以还没有文件。写进 CIS 的金额必须有来源；律师确认之后，后来的抽取不能盖掉它。

## 后段加什么

阶段 2 到阶段 6 不增加新的运行平台。

支出表、资产类别、已确认金额和 CIS 映射是 Postgres 里的新表，加上现有 Next.js 页面。映射是确定性代码：格子对应已确认事实或问卷答案。缺来源就留空。

两件耗时工作不放在用户请求里：

- 从文件里抽出数字
- 把 CIS 草稿和已接受附件打成 PDF

它们做成后台任务，读 S3，把结果写回 Postgres。任务代码用 TypeScript。文件仍在 S3，数字仍在原来的库。

## 明确不采用

- 不用 Spring Boot 做网站或 API。
- 不用 RDS 替换 Supabase 的 Postgres。
- 不用公开的 S3 网址。
- 不把 `service_role` 或 AWS 密钥放进浏览器。
- 不在阶段 1 预建一套空的 Java 服务。

只有团队里写 Java 明显更快，才把后台任务单独做成 Spring Boot。页面、权限和数据库仍按本文。那是以后的决定，不是现在的架构。
